# Учёт автомобилей v2.0 - Серверная версия с авторизацией

## 🔐 Система авторизации

### Режимы работы:

1. **Полный доступ** (после входа):
   - Просмотр данных
   - Добавление/удаление записей
   - Редактирование тарифов
   - Загрузка/сохранение файлов
   - Экспорт в Excel

2. **Только просмотр** (без входа):
   - Просмотр всех данных
   - Экспорт в Excel
   - **НЕТ** доступа к редактированию
   - **НЕТ** блокировки данных
   - Скрыты кнопки: Добавить, Удалить, Загрузить, Импорт тарифов

### Вход в систему (Active Directory):

Регистрации, логинов и паролей **нет**. Приложение работает в корпоративной сети,
где reverse-proxy (IIS с Windows Authentication / Apache mod_auth_gssapi / Nginx+Kerberos)
автоматически определяет пользователя по учётной записи Windows (Kerberos/NTLM)
и передаёт его AD-логин на сервер.

1. При открытии сайта появится экран входа
2. Нажмите **«✏️ Вход для редактирования»** — сервер сам определит вас по Active Directory
3. Если ваш AD-логин есть в allow-list (`users.json`) и вы проходите по группам —
   откроется режим редактирования; иначе будет показана причина отказа

### Фильтрация пользователей (users.json)

Пускать или не пускать человека на редактирование решает файл `users.json` на сервере:

```json
[
  { "id": "u1", "username": "ivanov@corp.local", "displayName": "Иванов И.И.", "allowed": true,  "adGroups": [] },
  { "id": "u2", "username": "petrov@corp.local", "displayName": "Петров П.П.", "allowed": true,  "adGroups": ["logistics-editors"] },
  { "id": "u3", "username": "sidorov@corp.local","displayName": "Сидоров С.С.","allowed": false, "adGroups": [] }
]
```

- `username` — SAM-логин или UPN из Active Directory (`DOMAIN\user` и `user@domain` считаются одинаковыми);
- нет логина в файле → доступ на редактирование запрещён;
- `allowed: false` → запрещено (уволился/перевёлся), файл правится администратором без перезапуска;
- `adGroups` — пустой массив = группа не важна; непустой = нужна хотя бы одна из перечисленных групп
  (proxy должен передавать их в заголовке `X-Forwarded-Groups`).

Имена заголовков настраиваются переменными окружения сервера:
`AD_USER_HEADER` (по умолчанию `X-Forwarded-User`), `AD_DISPLAY_NAME_HEADER` (`X-Forwarded-Name`),
`AD_GROUPS_HEADER` (`X-Forwarded-Groups`).

### Отладка входа по Active Directory (DEBUG_AD)

Если при «Входе для редактирования» появляется ошибка «Не удалось определить пользователя из Active Directory»,
запустите сервер с отладочным выводом:

```bash
DEBUG_AD=1 node server.js
```

Что даёт этот режим:
- в консоль сервера логируются **все заголовки** входящего запроса `/api/auth/whoami`
  (чувствительные — Cookie/Authorization — маскируются);
- в ответе 401/403 дополнительно приходит объект `debug`, и его содержимое показывается
  прямо на экране входа в браузере: какой заголовок искал сервер, что реально передал прокси,
  какие «похожие на AD» заголовки присутствуют, какие логины разрешены в users.json;
- там же печатается подсказка с частыми вариантами имён заголовков:
  `x-remote-user`, `remote_user`, `x-forwarded-user`, `authorization-user`.

Типичная причина ошибки: прокси передаёт логин в заголовке с другим именем. Найдите его
в списке `presentAuthHeaders` и запустите сервер с этим именем, например:

```bash
AD_USER_HEADER=x-remote-user DEBUG_AD=1 node server.js
```

Если похожего заголовка нет вообще — Windows-аутентификация на прокси не настроена
(или браузер не отдаёт Kerberos/NTLM-билет: проверьте, что сайт в зоне «Локальная intranet»
в настройках Internet Explorer/Edge и что к сайту обращаются по доменному имени, а не по IP).

Сервер теперь сам различает три ситуации и пишет вывод в тексте ошибки:
1. запрос пришёл без каких-либо дополнительных заголовков → скорее всего, браузер
   открыт напрямую на Node-сервер (в обход прокси) — открывайте адрес прокси;
2. есть `x-forwarded-for`/`x-real-ip`, но логина нет → прокси не подставляет заголовок
   с пользователем (нужно правило REMOTE_USER/LOGON_USER → X-Forwarded-User);
3. есть неизвестные заголовки → вероятно, логин приходит в одном из них,
   посмотрите `allHeaders` в отладке и задайте `AD_USER_HEADER=<имя заголовка>`.

### Быстрая проверка входа без прокси (MOCK_AD_USER)

Чтобы убедиться, что users.json и логика допуска работают, можно временно
подставить себе AD-логин. Это работает ТОЛЬКО при обращении с той же машины
(127.0.0.1), поэтому удалённые пользователи обойти фильтрацию не смогут:

```bash
MOCK_AD_USER=shavlakovav@nsk.tlcn.ru node server.js
# и откройте http://localhost:3001 на этом же сервере
```

В консоли появится строка `🧪 whoami: использован MOCK_AD_USER=...`.
Для боевого запуска переменную уберите.

Когда проблема решена, уберите `DEBUG_AD` — в обычном режиме эти данные наружу не отдаются.

### Режим только просмотра:

На экране входа нажмите кнопку **«🔍 Только просмотр»** — она доступна всем без исключения.

В этом режиме:
- Не требуется никаких учётных данных и разрешений
- Данные не блокируются (никаких записей в lock.json)
- Можно просматривать и экспортировать
- Нельзя редактировать, автосохранение на сервер полностью отключено

### Переключение режимов:

⚠️ **Важно**: Переключиться между режимами нельзя!

- Если вошли через **"Только просмотр"** — остаётесь в этом режиме до закрытия вкладки
- Если прошли **"Вход для редактирования"** (Active Directory) — всегда в режиме редактирования
- Чтобы сменить режим — нужно **выйти** и войти заново

Нажмите кнопку **"🚪 Выход"** в шапке

## 🔒 Система блокировок

Приложение использует систему блокировок для предотвращения одновременного редактирования данных несколькими пользователями.

### Как это работает:
1. При первом изменении данных клиент автоматически устанавливает блокировку
2. Блокировка действует **30 минут** и автоматически продлевается каждые 10 минут

### Визуальный индикатор блокировки (в шапке):
- 🔒 **Заблокировано: Вами** (зелёный текст) — если текущий пользователь заблокировал данные
- 🔒 **Заблокировано: [Имя]** (красный текст) — если другой пользователь заблокировал данные
3. Другие пользователи видят, кто заблокировал данные (имя пользователя)
4. При закрытии вкладки блокировка автоматически освобождается

### Информация о блокировке:
- **userId** - уникальный идентификатор пользователя (генерируется автоматически)
- **computerName** - определяется по User Agent (Windows PC / Mac / Linux)
- **lockedAt** - время установки блокировки
- **expiresAt** - время истечения блокировки

### Файлы:
- `data.json` - основные данные приложения
- `lock.json` - информация о текущей блокировке

---

## 🔄 Синхронизация данных

- Данные автоматически сохраняются на сервер через **2 секунды** после изменения (debounce)
- При ошибке сервера данные сохраняются в localStorage как резервная копия
- При загрузке приложения данные загружаются с сервера, если сервер недоступен - из localStorage

## 🆘 Решение проблем

### Ошибка "Не удалось загрузить данные с сервера"
- Проверьте, что сервер запущен (`npm run server`)
- Убедитесь, что порт 3001 не занят
- Проверьте CORS настройки в `server.js`

### Данные не сохраняются
- Проверьте права доступа к папке проекта
- Убедитесь, что файл `data.json` может быть создан
- Проверьте логи сервера в консоли

### Блокировка не снимается
- Удалите файл `lock.json` вручную
- Подождите 30 минут (автоматическое истечение)
- Перезапустите сервер
